# Worked example: ctx's own context

This example shows a populated default scaffold and how it evolves during
development. The project is ctx itself: its domain is context lifecycle and
sharing rules, not checkout or subscriptions.

The facts were checked against ctx **0.4.0**, commit
`57c719617a570a0f66cc560d380d1b480ab51b74`, on **2026-10-07**.
[Reference metadata](reference.json) records that point. This is a reference
snapshot, not a promise that later source still matches. Recheck relevant
source and tests before using its claims in a newer checkout.

## Explore the filled documents

The [stored scaffold](scaffold/README.md) contains the durable files that would
live in a ctx checkout's `.ctx/`. The continuation is stored separately as
[CONTINUE.example.md](CONTINUE.example.md): an illustrative checkpoint, not
this repository's actual working state.

| Document | What to notice |

| [Scaffold README](scaffold/README.md) | Managed guidance stays separate from the project-owned pointer |

The resulting *active* layout looks like this:

```text
.ctx/
├── .gitignore
├── config.json
├── README.md
├── INDEX.md
├── context/
│   ├── overview.md
│   ├── behavior.md
│   ├── behavior/
│   │   └── initialization.md     # authored during filling, not generated by ctx
│   ├── architecture.md
│   ├── caveats.md
│   └── glossary.md
└── local/
    └── CONTINUE.md              # live state stays ignored
```

The stored snapshot deliberately has no `local/CONTINUE.md`. Its separate
sample illustrates that file without changing the Git-sharing boundary.
The snapshot is not an active scaffold: do not point ctx at its storage
directory. Metadata source paths such as `pkg/ctx/init.go` are relative to
the **ctx repository root**, not to this documentation directory.

## Start with generated structure

Use a disposable ctx checkout with no existing `.ctx/` and an installed ctx
CLI. Run these commands from that checkout's root:

```bash
ctx init
ctx doctor
ctx status
git status --short .ctx
```

Initialization creates the core plus behavior and glossary in team mode. It
does not inspect source or populate project facts. `doctor` can pass while
`status` exits non-zero because the documents are still draft. Selected status
lines at this stage are:

```text
✗ context/behavior.md — draft
✗ context/glossary.md — draft
```

Durable files are available for review; `.ctx/local/CONTINUE.md` is ignored.
Nothing has been staged or committed by ctx.

## Fill from evidence

Ask a developer or coding agent to inspect the repository. A useful task
request is:

> Follow the owner's instructions. Fill the installed project-fact documents
> from current source and tests. Keep each concern in its owning document,
> leave unknowns draft, and record supporting repository-relative paths.
> Keep INDEX concise. Do not stage or commit anything.

For this example, that inspection starts at
[the CLI entrypoint](../../../cmd/ctx/main.go),
[command definitions](../../../pkg/ctx/root.go), and
[the layout/add-on catalog](../../../pkg/ctx/catalog.go), then follows the
relevant lifecycle implementations and tests.

Compare the generated prompts with the populated documents above. Each fact
document has concrete claims and evidence; the instructional notes and empty
tables have been removed. No checked-in agent instruction file was found at
the reference revision, so the project-owned pointers say so instead of
inventing an `AGENTS.md` or treating context as authority.

Only after checking claims, set `status` to `verified`, record the actual
commit from `git rev-parse HEAD` plus the verification date, and list the
supporting source paths. Do not copy this example's verification hash to a
different project or revision.

```bash
git rev-parse HEAD
ctx doctor
ctx status
git diff -- .ctx
git status --short .ctx
```

At the recorded revision, unchanged listed sources produce ready checks. For
example, the behavior document reports:

```text
✓ context/behavior.md — verified at 57c719617a570a0f66cc560d380d1b480ab51b74 @ 2026-10-07
```

`status` checks evidence paths and freshness, not whether the prose is true.
The human reviews the files and decides what durable context to stage and
commit. Never force-add the ignored continuation.

## Use and grow context during a task

Suppose the next task is: **explain what happens when a developer runs init in
a fresh clone containing shared team context**.

Read the owner's instructions and local continuation, then INDEX's behavior
route. The behavior parent links to
[initialization and fresh-clone hydration](scaffold/context/behavior/initialization.md).
That child contains the relevant decisions and outcomes. Read architecture
only if tracing how they are implemented; glossary only if a term is unclear.
There is no need to load every context document.

The child was created by the developer or agent during filling, after
identifying a coherent topic. ctx generated only `context/behavior.md`.
The parent keeps shared concepts and cross-command rules; the child owns the
deeper initialization decisions and carries its own metadata.

As more topics earn detail, create additional children and link them from the
owning parent. Do not pre-create empty workflow files. Update the local
continuation at meaningful checkpoints; the separate
[sample](CONTINUE.example.md) shows what a mid-task checkpoint can look like.

## Reconcile after supporting code changes

Later, suppose a task changes initialization rules in `pkg/ctx/init.go`.
`ctx status` reports documents citing that path as not ready, including the
initialization child. An uncommitted source edit is enough; no new commit is
required for the freshness warning.

The developer or agent now:

1. Marks affected facts draft while reviewing the changed source and tests.
2. Updates the claims in their owning documents and adjusts routes if needed.
3. Records the new immutable source commit, date, and evidence after verification.
4. Runs `ctx doctor` and `ctx status` and reviews the shared-context diff.
5. Records remaining work in the local continuation.

A changed source path does not prove every claim in a document is wrong.
It signals that its recorded verification needs reconciliation.

When the installed CLI's templates change, also run:

```bash
ctx update
ctx doctor
ctx status
```

`update` refreshes managed guidance and scaffold metadata. It preserves filled
facts, authored children, and project-owned routing; it does **not** rewrite
facts, reverify them, install new defaults, or convert the visibility mode.

## Resume in a fresh clone

Once the human has committed durable team context, another developer gets
those files by cloning the repository. The ignored continuation is absent.
From the new clone's root:

```bash
ctx init
ctx doctor
ctx status
```

`init` hydrates only the missing local continuation and leaves shared facts
and configured add-ons unchanged. The developer fills continuation with
their own task and working-tree state; another person's session is not resumed
implicitly. If continuation already exists, init refuses to overwrite it.
Repeat `--folder` on commands if the shared scaffold uses a custom name.

## Add another concern deliberately

This snapshot shows the default experience, not every available add-on.
If a later task needs a dedicated compatibility document, the user can run:

```bash
ctx add --list
ctx add contracts
ctx doctor
ctx status
```

`add` installs a draft contracts template and refreshes config and INDEX
routing. The developer or agent must fill and verify it; `ctx status` exits
non-zero while the new document is draft. An older installed template revision
needs `ctx update` before `add`. The stored snapshot remains default-only.

## Keeping the example trustworthy

The repository's Go tests check the example's metadata, source paths, local
document links, routes, and scaffold compatibility. An isolated repository
also exercises readiness, changed-source detection, update preservation,
Git visibility, and fresh-clone hydration using the example documents.

Those checks do not certify factual truth. When updating the reference
snapshot, reread the cited source and tests, update
[reference.json](reference.json) and affected metadata together, then run:

```bash
go test ./pkg/ctx -run TestPopulatedContextExample -count=1
```

See the [fill-context workflow](../../fill-context-workflow.md) for the general
process and [layout guide](../../layout-v2.md) for the persisted contract.
